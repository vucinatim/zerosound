# ZeroSound v0.8 Room Rewrite

Status: approved product and architecture direction

Target: v0.8

Scope: clean replacement of the role-based session model and its UI

## Goal

ZeroSound should feel like entering a real shared office room, not configuring a network audio
system. A person opens the menu bar or app, sees nearby rooms, and joins or creates one immediately.
Every connected Mac appears as an equal room member and speaker. One member is the current audio
source, and that responsibility can move without destroying the room.

The rewrite is complete only when the product, domain model, transport, and UI all use the same room
concept. A room-shaped UI on top of the existing Master/Receiver implementation is explicitly not an
acceptable outcome.

## Product contract

### Two-click entry

Creating or joining a room takes at most two intentional ZeroSound clicks.

From the menu bar:

1. Click the ZeroSound menu-bar icon.
2. Click a visible room or **Create Room**.

From outside the main app:

1. Open ZeroSound.
2. Click a visible room or **Create Room**.

There is no role selector, setup wizard, confirmation dialog, or mandatory room-name form. The
first room name defaults to **Office Room** and is remembered. It can be renamed later.

Joining a room automatically makes the Mac an active speaker after synchronization. Creating a room
joins it immediately but does not begin capturing system audio until someone chooses to play from
their Mac.

### One room screen

The main window has one primary screen rather than separate Session and Devices destinations.

It contains:

- the room name, member count, and overall health;
- the current audio source and a restrained live level/waveform;
- a responsive visual arrangement of two to eight Macs;
- a stable bottom action area for audio and room actions;
- diagnostics available as an inspector or expandable surface.

The visual arrangement communicates membership and responsibility, not literal speaker placement.
The source Mac is centered or elevated, and the remaining members arrange around it. Manual floor
plans, dragging, and fake spatial-audio positioning are out of scope.

### Equal members and transferable audio

“Master” and “Receiver” disappear from all user-facing language.

Every joined Mac is a `RoomMember`. Exactly zero or one member is the `AudioSource`. Any member can
choose **Play from this Mac**. If another source is active, ZeroSound clearly explains that the
existing stream will stop before the source changes.

The network still needs coordination, but `Coordinator` is an internal responsibility and never a
user role. The coordinator and audio source are separate concepts.

If the audio source leaves, the room remains and becomes idle. If the coordinator leaves, the
remaining members elect a replacement and retain the room membership. Continuing the old audio is
not expected when its source leaves.

### Menu-bar experience

The menu bar is a compact room remote, not a miniature copy of the main window.

Offline it shows:

- nearby rooms with member counts and current source summaries;
- **Create Room**;
- **Open ZeroSound** and **Quit**.

Inside a room it shows:

- room name, member count, and health;
- current audio source;
- **Play from this Mac** or **Stop audio**, when applicable;
- **Leave Room**;
- **Open Room** and **Quit**.

The app continues running after its main window closes. Sleep/wake, App Nap protection, reconnects,
and audio-device recovery remain owned by the app process rather than any window.

### Playback context

The reliable v0.8 presentation is:

> System audio from Boo’s Mac
>
> Chrome · Live audio

The source name and live audio level are required. Source-application identification is optional if
it can be implemented using stable system information. Exact YouTube, Spotify, or browser track
metadata is deferred until it can be supported without private APIs or app-specific fragility.

## Visual language

- Neutral macOS materials and surfaces in light and dark mode.
- One restrained ZeroSound blue for selection, source identity, and primary action.
- Green only for healthy/live state.
- Amber only for degraded/recovering state.
- Red only for explicit destructive actions.
- No saturated full-width cyan controls.
- No floating play/stop control in window chrome.
- No duplicated separators or decorative card borders around every element.
- The primary playback control has one consistent location in the main window.
- Healthy diagnostics remain quiet; only actionable degradation attracts attention.

## Domain model

The domain layer uses explicit value types and state machines rather than loosely related booleans.

### Stable identities

```swift
struct RoomID: Hashable, Codable, Sendable
struct MemberID: Hashable, Codable, Sendable
struct RoomDescriptor: Identifiable, Hashable, Sendable
struct RoomMember: Identifiable, Hashable, Sendable
```

`RoomID` persists for the life of a room. `MemberID` persists per ZeroSound installation so a
temporary disconnect does not create a new person in the room.

### Application membership state

```swift
enum MembershipState: Equatable, Sendable {
  case discovering
  case outsideRoom
  case creating(RoomID)
  case joining(RoomID)
  case inRoom(RoomSnapshot)
  case reconnecting(RoomID)
  case leaving(RoomID)
}
```

Only the state machine may transition membership. Views never coordinate networking directly.

### Audio-source state

```swift
enum AudioSourceState: Equatable, Sendable {
  case idle
  case assigning(MemberID)
  case priming(MemberID)
  case live(MemberID)
  case stopping(MemberID)
}
```

Source assignment is a room operation. Capture, timestamp conversion, broadcasting, local playback,
and UI state all derive from this single state.

### Coordinator state

The room protocol maintains a coordinator term and coordinator member ID. Election is deterministic
for the small LAN group and rejects state from older terms. Coordinator changes must not change the
room ID or force members to perform the join flow again.

The first implementation should remain deliberately small: one coordinator lease, monotonic terms,
member heartbeats, and deterministic successor selection. It should not grow into a generic
distributed-consensus framework.

## Module ownership

The existing Swift package remains small. New SwiftPM targets are added only when they create a real
dependency boundary; folders and focused types are preferred over target proliferation.

```text
ZeroSoundAudioIO/
  Core Audio capture callback and lock-free ring only

ZeroSoundCore/
  RoomDomain/
    identities, snapshots, state machines, commands
  RoomDiscovery/
    Bonjour advertisement and passive browsing
  RoomTransport/
    versioned control messages, membership, election, audio routing
  AudioPipeline/
    capture orchestration, packetization, jitter, drift, rendering
  Diagnostics/
    health aggregation and export
  ZeroSoundController.swift
    main-actor presentation model and use-case orchestration

ZeroSoundApp/
  Room/
    RoomView, member layout, member tile, action bar
  Discovery/
    nearby-room and create-room surfaces
  Diagnostics/
    room health inspector and member details
  MenuBar/
    compact room remote
  AppLifecycle/
    process-level sleep, wake, termination, and window behavior
```

### Ownership rules

- `ZeroSoundAudioIO` performs no networking, allocation in callbacks, or UI work.
- `RoomDomain` imports Foundation only and is deterministically unit-testable.
- Discovery discovers rooms; it does not join them.
- Transport moves typed room commands and audio; it does not decide UI state.
- The audio pipeline owns all renderer queues and timing decisions.
- The controller invokes use cases and publishes presentation state; it does not encode packets.
- Views render state and send user intent; they do not own timers, sockets, or reconnect logic.
- Every mutable subsystem has one concurrency owner: an actor, main actor, or private serial queue.
- Shared encoders, mutable globals, callback-driven boolean state, and cross-layer singleton access are
  prohibited.

## Room protocol

v0.8 introduces a new control-protocol version and intentionally rejects legacy role-based sessions.
There is no compatibility shim between the v0.7 Master/Receiver protocol and v0.8 rooms. Every Mac
in a room must run the new protocol.

Required operations:

- advertise and withdraw a room;
- publish a room descriptor for passive discovery;
- join, accept, reject, leave, and reconnect;
- publish authoritative member snapshots;
- heartbeat members and remove stale members;
- assign, release, and transfer the audio source;
- announce stream start, stop, and format changes;
- route audio from any assigned member through the room timeline;
- estimate clocks against the current coordinator;
- elect a replacement coordinator using a new term;
- report per-member playback health;
- reject incompatible protocol versions with a clear reason.

Control messages use explicit command and event types instead of adding unrelated optional fields to
one indefinitely growing message structure. Audio packets remain compact binary datagrams.

## Source transfer

Source transfer is a scheduled state transition, not a collection of start/stop callbacks.

1. A member requests the source role.
2. The coordinator validates current membership and publishes `assigning`.
3. The old source stops at the agreed boundary and renderers receive a stream stop marker.
4. The new source verifies capture permission and clock calibration.
5. The coordinator publishes a future room-timeline anchor.
6. The new source begins packet delivery against that anchor.
7. Members prime and fade in together.
8. The coordinator publishes `live` after the stream is established.

Failure returns the room to `idle` or the previous valid source; it never leaves mixed ownership.
The first release targets a clean handoff rather than uninterrupted continuation of content from a
different computer.

## Diagnostics model

The normal room screen exposes one aggregate state:

- Excellent
- Good
- Recovering
- Needs attention

The inspector provides evidence behind that state:

- member connection and compatibility state;
- current and worst round-trip latency;
- playback queue depth;
- concealed and reordered packets;
- renderer underruns and successful resynchronizations;
- clock correction;
- reported output-device latency;
- capture drops on the active source;
- coordinator term and source assignment in copied technical diagnostics only.

Thresholds live in one diagnostics policy type and are tested. Views do not independently invent
health colors or severity rules.

## Rewrite strategy

The working v0.7 build remains the behavioral reference while v0.8 is built. The rewrite proceeds in
vertical replacements, and all legacy code is deleted before release.

### Phase 0 — Baseline and invariants

- Preserve deterministic tests for clock estimation, packet encoding, jitter handling, drift, and
  renderer recovery.
- Record current release CPU, memory, packet rate, and buffer behavior.
- Identify audio-pipeline types that remain correct independent of the session model.

Exit condition: timing and continuity invariants are documented and protected by tests.

### Phase 1 — Pure room domain

- Add stable room/member identities.
- Implement membership, audio-source, and coordinator state machines.
- Define typed commands, events, snapshots, and transition errors.
- Add exhaustive deterministic transition tests.

Exit condition: the complete room lifecycle can be simulated without Network, AVFAudio, or SwiftUI.

### Phase 2 — Discovery and two-click entry

- Replace master-only Bonjour discovery with passive room discovery.
- Advertise room ID, display name, protocol version, member count, and source summary.
- Implement create/join/leave use cases.
- Persist the room display name and preferred recent room.

Exit condition: menu bar and window can create or join a visible room within the two-click contract.

### Phase 3 — Membership and coordinator continuity

- Implement authoritative member snapshots and heartbeats.
- Implement reconnect without duplicate members.
- Implement coordinator terms, election, and stale-term rejection.
- Add deterministic transport simulations for loss, reorder, duplicated events, and coordinator exit.

Exit condition: the room survives a non-source member leaving, network interruption, and coordinator
exit without requiring members to join again.

### Phase 4 — Transferable audio source

- Route captured audio from the assigned member into the coordinator timeline.
- Implement scheduled source assignment, release, and transfer.
- Reuse the proven capture, jitter, drift, concealment, recovery, and latency-compensation pipeline.
- Ensure old source packets cannot enter a new source generation.

Exit condition: any joined Mac can become the source, and all members converge on one source and one
stream generation.

### Phase 5 — Single-room application UI

- Replace the sidebar shell with discovery and room states in one window.
- Implement the adaptive member layout and source emphasis.
- Add the stable action bar and restrained live audio visualization.
- Remove floating toolbar playback controls and duplicated status surfaces.
- Validate light mode, dark mode, reduced motion, keyboard access, and VoiceOver labels.

Exit condition: no Master/Receiver terminology or role selector remains in the product UI.

### Phase 6 — Menu-bar remote

- Reduce the current menu panel to room discovery and essential room controls.
- Verify create, join, play, stop, leave, reopen, and quit behavior with the main window closed.
- Keep lifecycle observation at process scope.

Exit condition: all menu-bar actions operate correctly without an open application window.

### Phase 7 — Diagnostics and polish

- Implement aggregate room health and the diagnostics inspector.
- Add copyable room and member diagnostics.
- Apply the final color, spacing, animation, empty-state, and error-state system.
- Add optional source-application context only if it passes the stability boundary.

Exit condition: ordinary users see a calm room; technical evidence remains one interaction away.

### Phase 8 — Deletion, hardening, and release

- Delete the legacy `Role`, `MasterServer`, `MasterBrowser`, `ReceiverConnection`, and role-shaped
  controller APIs after their replacements are proven.
- Delete the legacy sidebar sections and obsolete Session/Devices views.
- Remove compatibility adapters, unused preferences, dead messages, and duplicate status strings.
- Run formatting, unit tests, Thread Sanitizer, integration tests, release profiling, and archive
  verification.
- Run mixed-hardware office soak tests with two, five, and eight Macs.

Exit condition: v0.8 contains no dormant legacy architecture and produces one verified universal
release artifact.

## Test strategy

### Deterministic unit tests

- valid and invalid membership transitions;
- duplicate joins and stable member identity;
- source assignment, rejection, cancellation, failure, and generation fencing;
- coordinator election and stale-term rejection;
- protocol round trips and incompatible-version rejection;
- jitter loss, reorder, burst loss, underrun, and recovery;
- diagnostics policy thresholds.

### Integration tests

- create and discover a room;
- join two simulated members;
- source audio from coordinator and non-coordinator members;
- transfer the source while packets are in flight;
- disconnect and reconnect without duplicate members;
- remove the coordinator and elect a successor;
- reject audio from a stale source generation;
- close every window while the room continues through the menu-bar process.

The integration harness uses injectable clocks and an in-process transport simulation. Bonjour and
real UDP receive a smaller set of macOS integration checks; core correctness must not depend on flaky
wall-clock tests.

### Manual release validation

- two-, five-, and eight-Mac room layouts;
- different built-in output devices and sample rates;
- congested Wi-Fi, interface changes, sleep/wake, and output-device changes;
- system-audio permission denied, granted, and later revoked;
- source Mac leaving during playback;
- coordinator leaving during idle and live playback;
- VoiceOver, keyboard navigation, reduced motion, light mode, and dark mode;
- AirDrop installation and protocol mismatch messaging.

## Performance and reliability guardrails

- No locks, allocation, logging, or networking in the Core Audio callback.
- No unbounded packet, member, event, or diagnostics collections.
- No polling on the main actor.
- Audio packet encoding occurs once per packet, independent of room size.
- Member/status events are coalesced before UI publication.
- Source and coordinator generations fence every asynchronous callback.
- A reconnect cannot revive a stopped or replaced room session.
- Release CPU and memory must not regress materially from the v0.7 baseline.
- Joining should reach synchronized speaker readiness within two seconds on a healthy LAN.
- A transient network failure should reconnect within five seconds when the room remains visible.
- Source transfer should produce a bounded, faded interruption rather than a click, overlap, or
  permanently shifted timeline.

## Explicit non-goals for v0.8

- true surround channels or physical speaker-position modeling;
- manual room floor plans;
- uninterrupted continuation of one Mac’s YouTube playback on another Mac;
- exact cross-application track metadata;
- WAN or internet rooms;
- lossy codec or forward-error-correction work without measurements;
- generic distributed-consensus infrastructure;
- compatibility with the v0.7 role-based protocol.

Authenticated pairing and encrypted audio remain required before ZeroSound is appropriate for an
untrusted LAN. The v0.8 protocol must leave a clean authorization boundary, but adding a pairing
prompt to the trusted-office two-click flow is not part of this rewrite.

## Definition of done

v0.8 is done only when all of the following are true:

- nearby rooms are visible before joining;
- create and join meet the two-click rule in the menu bar and main app;
- joining automatically makes the Mac a synchronized speaker;
- all room members see the same roster and audio source;
- any member can become the source through the room protocol;
- source and coordinator are separate domain concepts;
- the room survives coordinator replacement without a new join flow;
- the main window is a single room experience with an integrated diagnostics inspector;
- closing the window leaves the room and menu controls active;
- health severity comes from one tested policy;
- all legacy role-based code and UI are deleted;
- deterministic, sanitizer, integration, and manual office tests pass;
- the optimized universal app and AirDrop archive validate successfully;
- remaining limitations are accurately documented.

## Locked decisions

- Default room name: **Office Room**, remembered and editable later.
- Joining means joining as an active speaker.
- All members are peers in the UI.
- Coordinator is internal and automatically replaceable.
- Audio source is singular and transferable.
- Source takeover is initiated locally and clearly warns when it will stop another source.
- Main app uses one room screen.
- Menu bar provides discovery and essential quick actions only.
- Diagnostics are integrated but visually subordinate to the room.
- v0.8 is a clean protocol and architecture break from v0.7.
